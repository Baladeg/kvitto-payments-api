# Работа с ИИ

Инструмент: Codex desktop, диалог с ИИ и встроенный терминал PowerShell.
Этап анализа выполняла предыдущая модель этого же чата; её точное имя в доступном
контексте не указано. Этап реализации выполняется Codex на базе GPT-6.
Использованы чтение PDF через pypdf, визуальная проверка трёх страниц через Poppler,
официальная документация SQLAlchemy, PostgreSQL и FastAPI, установка зависимостей
и команды проверки проекта. Для реализации другие ИИ-инструменты не использовались;
аудит Astra отражён отдельно ниже со слов пользователя.

Ключевые запросы пользователя:

1. Изучить PDF и compose.yaml, не писать код, составить требования, модель,
   денежные расчёты, конкурентную идемпотентность, транзакции, тесты и план.
2. Приоритет: строгое соответствие ТЗ, простая архитектура и возможность объяснить
   каждую строку на собеседовании с CTO.
3. Реализовать утверждённый план с `ON CONFLICT DO NOTHING RETURNING`,
   `SELECT FOR UPDATE`, отдельной БД `kvitto_test`, выполнить реальные проверки
   и не публиковать код на GitHub.

Найденные недостатки и уточнения:

- В исходном проектном ограничении рассрочки не хватало явного
  `installment_months IS NOT NULL`. При анализе перед реализацией обнаружено:
  PostgreSQL CHECK пропускает NULL. В модель добавлена явная проверка, а в тесты —
  попытка вставить рассрочку без срока непосредственно в БД.
- В плане идемпотентности требовалось уточнить порядок проверки тарифа:
  согласованное поведение повтора с другим валидным телом требует искать известный
  ключ до поиска тарифа. Этот порядок реализован и покрыт отдельным сценарием.
- Каталог `docs` отсутствовал. Для анализа использован реально доступный PDF из
  Downloads. Доступ к состоянию Docker при анализе потребовал разрешения среды.
- Starlette 1.9.0 объявила TestClient с httpx устаревшим в пользу httpx2. По ТЗ нужен
  httpx, поэтому тестовая зависимость ограничена `starlette>=0.46,<1`.

Фактические проверки 19.10.2026: зависимости установлены в существующее `.venv`
(Python 3.14.4), создана отдельная PostgreSQL-БД `kvitto_test`. Первый pytest:
96 passed, одно предупреждение Starlette/httpx. После переустановки зависимостей
повторный `python -m pytest -q`: **96 passed, 1 warning in 3.61s**. Оставшееся
предупреждение — устаревающий alias `anyio.abc.BlockingPortal` внутри Starlette
0.52.1; оно не подавлялось. `pip check`: No broken requirements found.

Через реальный Uvicorn и HTTP проверены основная БД (тарифы, Swagger, OpenAPI,
404/422 без создания платежей) и полный сценарий на `kvitto_test` через `curl.exe`:
создание 201, повтор 200, точная скидка и график, вебхук 200, запрещённый переход
409 с прежним статусом. Отдельный защитный запуск с `TEST_DATABASE_URL` на `kvitto`
ожидаемо остановлен фикстурой до инициализации/очистки (pytest exit 1).
Серверы для ручных проверок остановлены. Compose не изменялся, публикации не было.

## Бонусы HMAC, GitHub Actions и AGENTS.md, 19.10.2026

Пользователь сообщил о публикации обязательной части в Baladeg/kvitto-payments-api
и запросил три бонуса, сохранение исходных 104 сценариев, подписанный пример
PowerShell и проверки без push/PR/merge. После git fetch origin main до изменения
файлов создана локальная ветка feat/bonus-hmac-ci от актуальной origin/main 30d8f5f.
Работу выполнял Codex в этом чате; сверены официальные документы Python hmac и
GitHub Actions по PostgreSQL service, checkout и setup-python.

Решение: WEBHOOK_SECRET обязателен на startup, пустое/пробельное значение приводит
к явной ошибке до открытия БД. Небольшой middleware проверяет только банковский POST
по исходным байтам request.body() до валидации JSON. Формат X-Signature — один
заголовок с 64 hex-символами, сравнение digest через hmac.compare_digest. Отсутствие,
неверное значение, повреждение и дубли заголовка дают 401. Транзакционные сервисы,
денежные расчёты и разрешённые переходы не менялись. Старые webhook-тесты теперь
подписывают те же байты, которые отправляют, с временным случайным тестовым ключом.

Первоначальные попытки pytest завершались ошибками fixture из-за ConnectionTimeout:
Docker Desktop оказался выключен. Он запущен, затем существующий PostgreSQL поднят
командой docker compose up -d --wait db без редактирования compose.yaml. Ruff нашёл
12 замечаний: импорты, вложенные with и лишний replace('Z', '+00:00') в тесте даты.
Они исправлены минимально; datetime.fromisoformat понимает Z на Python 3.11+.
Правила линтера, предупреждения и тесты не отключались.

Первый успешный полный pytest: 125 passed, 1 warning in 4.53s; финальный полный
прогон после HTTP-проверок: **125 passed, 1 warning in 4.82s**. Добавлен 21 случай
корректной/отсутствующей/неверной/повреждённой подписи, исходных байтов, дублей,
не-ASCII заголовка, подписанного/неподписанного плохого JSON и отказа startup.
Сравнение AST подтвердило сохранение всех 29 исходных тестовых функций и их
параметризаций (104 случая), а также неизменность бизнес-моделей, схем и сервисов.

Ruff 0.17.1: All checks passed!; pip check: No broken requirements found.
Пример README выполнен через настоящий Uvicorn на kvitto_test в доступном

## Исправление обхода HMAC через root_path, 19.10.2026

Пользователь передал результат независимого аудита Astra: P1 в бонусной ветке
feat/bonus-hmac-ci. Требовалось устранить обход HMAC при root_path, привязать
проверку к маршруту до разбора JSON, сохранить прежнюю бизнес-логику и проверить
исправление без commit/push/merge. Работу выполнял Codex в этом чате.

Причина: middleware сравнивал request.url.path с фиксированным /webhooks/bank,
а маршрутизатор учитывал ASGI root_path и мог выбрать вебхук для пути с префиксом.
Вначале добавлен регрессионный тест. До исправления запуск с maxfail=1 завершился
результатом 1 failed, 8 passed, 48 deselected: при root_path=/api запрос на
/api/webhooks/bank без подписи получил 200 вместо 401.

Middleware заменён на SignedBankWebhookRoute, наследник APIRoute, подключённый
только к маршруту банковского вебхука через APIRouter. Его get_route_handler
оборачивает штатный обработчик: после выбора маршрута, но до чтения JSON и
разрешения зависимостей проверяются формат подписи и HMAC исходных request.body().
Используется hmac.compare_digest; отсутствие, неверная или повреждённая подпись
дают прежние 401. Выбор защищаемого обработчика теперь выполняет сам маршрутизатор,
ручного сравнения или удаления префиксов пути нет. Обязательный непустой секрет
на startup, денежные расчёты и транзакции не менялись.

Добавлены 47 регрессионных случаев: root_path пустой, /api и /api/v1; ASGI-пути
с префиксом и без него; корректная/отсутствующая/неверная/повреждённая подпись;
неподписанный и подписанный повреждённый JSON; похожие префиксы /apix и /api/v1x,
а также лишние сегменты пути. Немаршрутизируемые пути получают 404, а запросы
к вебхуку без действительной подписи — 401 без изменения платежа. Все предыдущие
125 случаев сохранены. Полный pytest на kvitto_test: **172 passed, 1 warning in
7.93s**. Предупреждение Starlette/AnyIO осталось видимым.

Первый Ruff после правки указал на оформление длинного импорта FastAPI; импорт
разбит на строки. Итоговые ruff check . и pip check успешны: All checks passed!
и No broken requirements found. git diff --check не нашёл ошибок пробелов.
AST моделей, функций БД, схем и транзакционных сервисов совпадает с main 30d8f5f.

Через настоящий Uvicorn на PostgreSQL 16.15, только kvitto_test, последовательно
проверены root_path="", /api и /api/v1. Во всех трёх случаях отсутствующая,
неверная и повреждённая подписи вернули 401, полный ответ платежа не изменился.
Неподписанный повреждённый JSON дал 401, подписанный — 422; похожий путь — 404.
Действительная подпись дала 200 и succeeded, повтор — точный 409
{"error":"invalid_transition"}, действительный refund — 200 и refunded.
Все проверочные серверы остановлены, созданные платежи удалены из kvitto_test;
после проверки в ней ноль платежей. Основная БД не использовалась.
Коммит, push и merge не выполнялись; HEAD остался 30d8f5f в feat/bonus-hmac-ci.
